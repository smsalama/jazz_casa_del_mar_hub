# ADR-0003: Embedded SQLite (better-sqlite3) with Drizzle migrations as the only data store

- Status: Proposed (for T2); a deviation from the agency default (PostgreSQL), so Steven confirms it at T2
- Date: 2026-10-15
- Author: System Architect (P4-T2)
- Requirements: OQ-14, NFR-10, NFR-18, NFR-24 (parameterised queries), NFR-28 (sorting and search), NFR-31, NFR-32 (health check), NFR-33, NFR-35 (caps), FR-20, FR-22, FR-23, FR-38, FR-42, FR-43, FR-45, FR-48, US-43, US-46; threat model TM-04, TM-13, TM-45, TM-59

## Context

There is no database server on the client's server (OQ-14), and the agency default is PostgreSQL with migrations, Docker Compose on the Mac and PGlite in tests. The data is small: about 84 pages of content in four languages, fewer than 10 accounts, and caps of 50,000 enquiries and 50,000 subscribers (NFR-35). Writes are rare (staff saves, form posts limited to a few per hour per address). The store must survive a sudden stop after a confirmed write (NFR-33), take a consistent daily backup and restore it (FR-48), purge expired data every 24 hours (FR-45), and answer the NFR-10 admin queries quickly.

## Options considered

1. **PostgreSQL server** (agency default). Excluded by OQ-14 on the client's server; would also need Docker on the Mac and a different engine in the cloud workspace.
2. **PGlite** (PostgreSQL compiled to WebAssembly) in production and tests. Keeps PostgreSQL SQL, but runs one connection inside the Node.js process, holds the database in WebAssembly memory (tens to hundreds of MB), and its durability and online backup under a power cut on a long running server are far less proven than SQLite's. Server side commands (backup, purge, account unlock) cannot open the same data folder while the server holds it.
3. **SQLite through better-sqlite3**, a mature native binding with synchronous calls, an online backup API, and prebuilt binaries for macOS and Linux that need no install script.
4. **SQLite through the built-in `node:sqlite` module.** No dependency at all, but on Node.js 22 it still prints "SQLite is an experimental feature" (checked on 22.22.0 in the workspace).
5. **Plain JSON files.** No transactions, no concurrent access from the server side commands, hand built crash safety.

## Decision

Option 3: **SQLite 3.53.4 as bundled in better-sqlite3 13.0.3**, accessed through **Drizzle ORM 0.45.3**, with SQL migrations generated by **drizzle-kit 0.31.11** and committed to the web repo.

- One database file, `DATA_DIR/site.db`, in a folder that is never served (NFR-18) and whose permissions are owner only (checked at start, ADR-0015).
- Pragmas set on every connection: `journal_mode=WAL`, `synchronous=FULL` (a confirmed write survives a power cut, NFR-33), `foreign_keys=ON`, `busy_timeout=5000` (the server and a server side command can both open the file), `trusted_schema=OFF`, and `secure_delete=ON` (deleted rows are overwritten with zeros in the file, so purged personal data really leaves it; data model D-11). The retention purge ends with `PRAGMA wal_checkpoint(TRUNCATE)` so the write-ahead log no longer holds old page images (ADR-0010).
- All access through Drizzle query builders or prepared statements with bound parameters; raw SQL string building is banned by a lint rule (NFR-24). The only raw SQL is in reviewed migration files.
- **Migrations**: `npm run db:generate` (drizzle-kit) writes numbered SQL files to `migrations/`; `npm run db:migrate` applies them in one transaction each, recorded in Drizzle's migrations table. The server applies pending migrations at start only after writing a backup archive (ADR-0010), and refuses to start if a migration fails.
- **Tests use the same engine**: every test gets a fresh database file in a temporary folder (or `:memory:` for unit tests). This replaces the agency's PGlite approach and removes the gap between test and production engines.
- **Case and accent handling** (NFR-28, G-12): SQLite's `NOCASE` and `lower()` only fold ASCII. Every searchable value gets a stored normalised column computed in TypeScript: email addresses are trimmed and lower cased with `String.prototype.toLowerCase()` (Unicode aware, so Cyrillic works); names and references for search are also NFKD decomposed with combining marks removed. Searches compare normalised values; sorting for display uses `Intl.Collator` per language in TypeScript.
- **Health check** (NFR-32): `GET /healthz` runs a read and a one row write in a transaction on a `health` table.
- **Caps** (NFR-35): counted with indexed `count(*)` before insert.
- **Backup**: better-sqlite3's online backup API produces a consistent copy while the site runs (ADR-0010).

Main tables (the Database Engineer owns the detailed schema in `docs/data-model.md`): `site_state` (content revision, schema version), `install_secret` (suppression HMAC key), `account` (lockout counters as columns; there is no separate login attempt table), `session`, `content_entry`, `list_item`, `settings`, `legal_text_version` (wording archive, proposed pending T2, ADR-0004), `media_asset`, `media_variant`, `media_usage`, `enquiry`, `subscriber`, `suppression`, `rate_limit`, `used_form_token`, `security_event`, `job_run`, `backup_archive`, `health`, and `dsr_record` (created empty for FR-44 later).

## Consequences

- No database server, no Docker, the same engine on the Mac, the workspace and the client server. Install is `npm ci`.
- better-sqlite3 calls are synchronous. Every query is indexed and small; the largest (subscriber export, 10,000 rows) reads in keyset chunks of 500 rows with `.all()` and a `setImmediate` between chunks, not `.iterate()`, which would hold the connection busy between chunks (data model D-10); it is measured against NFR-10.
- One writer at a time. Fine at this write rate; WAL lets readers continue during a write.
- PostgreSQL features (row level security, `citext`, full text search in Postgres) are not available; none is required.
- SQLite itself is in the public domain, which is not a licence on the NFR-31 allow-list. It needs a recorded approval in the licence register (decision for Steven at T2, see `docs/architecture.md` section 17).
- If the client later wants PostgreSQL, Drizzle keeps the query code portable; the migration files and the backup format would change.

## Addendum 2026-10-16: Drizzle proof (task P6-T3)

Drizzle 0.45.3 and drizzle-kit 0.31.11 were proven against the schema on SQLite 3.53.4 with better-sqlite3 13.0.3.

| Feature | Result | Handling |
| --- | --- | --- |
| Table CHECK constraints, partial indexes, descending index columns, composite keys, foreign key actions | Expressed and emitted | In the Drizzle schema (all CHECKs are table level and named) |
| WITHOUT ROWID | Not expressible | `0000_baseline.sql` patched by hand for 7 tables; `npm run db:check` and tests verify it |
| Triggers and constant rows | Not expressible | Custom migrations `0001_integrity_triggers` and `0002_singleton_rows` |

- Migrations run through the project's own runner (one `BEGIN IMMEDIATE` transaction, refuses a database newer than the code), writing Drizzle's own `__drizzle_migrations` table so both agree.
- Migrations must always be generated with an explicit `--name` (`NNNN_snake_case`).
- The wording immutability trigger `legal_text_no_update` is limited to the content columns so that deleting an author account can set `created_by` to NULL (fix of 2026-10-16, also in `docs/data-model.md`).
